## 2026-07-17 (continuación 8) — Aclarando el archivo JSON exportado

El usuario exportó su config a `faro_servidores.json` y preguntó cómo armar uno a mano: qué poner en `id`, y notó que no traía ni alias ni credenciales.

- **`id` explicado:** no tiene que ser UUID, es cualquier string único; si se omite, se genera uno random al importar. Aclarado que si van a re-importar el mismo archivo repetidamente, conviene poner un id fijo a mano — de lo contrario cada import genera ids nuevos y las credenciales guardadas (ligadas al id viejo) quedan huérfanas.
- **Ambigüedad de nombres corregida:** la clave JSON de la base de datos que antes se llamaba `"name"` (el alias) ahora se llama **`"alias"`**, para que no se confunda con `"databaseName"` (el nombre real). `DatabaseEntry.fromJson`/`ServerConfigCodec` siguen aceptando `"name"` como fallback (compatibilidad con exports viejos). El campo Dart interno sigue llamándose `name` (no vale la pena renombrarlo en todo el código), solo cambió la llave del archivo.
- **Credenciales en el JSON, ahora opcional (decisión explícita del usuario, vía pregunta directa):** antes estaban excluidas sin excepción; ahora:
  - **Exportar** pregunta primero "¿Incluir credenciales?" con advertencia de que el archivo queda en texto plano si se aceptan — por defecto NO se incluyen.
  - **Importar** acepta `username`/`password` opcionales por servidor y por base de datos en el JSON; si vienen, se guardan automáticamente en `CredentialsRepository` (almacén seguro) al importar, con aviso en el diálogo de confirmación.

## 2026-07-17 (continuación 11) — Cancelación real de consultas

Antes de programar se le explicó al usuario una asimetría real entre motores: Postgres puede cancelar limpio (cerrar la conexión en curso interrumpe la consulta), pero SQL Server usa llamadas FFI que probablemente bloquean el isolate mientras esperan al servidor — nada de Dart (ni la señal de cancelar) puede correr hasta que esa llamada regrese sola. La única forma de interrumpirla de verdad es correrla en un Isolate aparte y matarlo a la fuerza. **El usuario pidió "real en ambos"**, aceptando la reestructura mayor que eso implica para SQL Server.

**Qué se construyó:**
- `CancellationToken` (movido a su propio archivo, `lib/data/datasources/cancellation_token.dart`, para evitar una dependencia circular entre `datasources` y `repositories`) ahora soporta `onCancel(callback)` — antes solo tenía la bandera `isCancelled` que se revisaba *después* de que `Future.wait` terminaba, sin interrumpir nada de verdad.
- `DbConnector.runQuery` ahora recibe `{CancellationToken? cancellationToken}`.
- `PostgresConnector.runQuery`: al cancelar, cierra la conexión (`conn.close()`) — cada consulta ya abría su propia conexión, así que esto solo afecta a esa consulta puntual. Cierre limpio con API pública, sin trucos.
- `SqlServerConnector.runQuery`: **reescrito para correr cada consulta en su propio `Isolate`** (función de entrada top-level, comunicación por `SendPort`/`ReceivePort` con mensajes JSON-safe). Al cancelar, se mata el isolate (`Isolate.kill(priority: Isolate.immediate)`) y el `Completer` se resuelve con error de inmediato — el usuario percibe cancelación instantánea, aunque la llamada nativa bloqueada puede seguir corriendo en segundo plano hasta desbloquearse sola y entonces el isolate ya muerto se descarta. **Se mantiene el `_serialized` (una consulta SQL Server a la vez, no en paralelo)** — la decisión de secuencialidad de antes no cambió, esto solo agrega la capacidad de cancelar; además ahora cancelar también libera la cola para las siguientes consultas encoladas, en vez de quedarse trabadas detrás de una que cuelga.
- `testConnection` de SQL Server se quedó como estaba (llamada rápida en el isolate principal, sin botón de cancelar en la UI, no vale la pena la complejidad del isolate ahí).
- Nuevo test unitario `test/cancellation_token_test.dart` (4 casos) cubriendo el registro de listeners antes/después de cancelar.

**2. **3. Tabla de resultados reescrita dos veces, terminando en un grid 2D real:**
- **Primer intento:** `ListView.builder` (virtualiza filas) anidado dentro de un `SingleChildScrollView` horizontal — funcionó para virtualizar, pero el usuario reportó que no tenía "ningún scroll para subir y bajar" arrastrable. ## 2026-07-22 (continuación) — `OPENQUERY` de SQL Server fallaba por opciones ANSI

El usuario, probando en el equipo de un cliente, reportó que un `OPENQUERY` desde SQL Server fallaba en Faro mencionando algo de "ANSI", pero corría bien en SSMS. Diagnóstico (sin necesitar reproducirlo, es un problema muy documentado de SQL Server): SSMS abre cada conexión con un set fijo de opciones `SET` (`ANSI_NULLS`, `ANSI_WARNINGS`, `QUOTED_IDENTIFIER`, etc.) — el conector de Faro (`sqlserver_connector.dart`, FreeTDS vía `mssql_connection`) no las configura en absoluto. `OPENQUERY`/consultas a servidores vinculados **exigen** específicamente `ANSI_NULLS` + `ANSI_WARNINGS` (si no, SQL Server tira el error 7405, cuyo texto literal es "Heterogeneous queries require the ANSI_NULLS and ANSI_WARNINGS options...") — coincide exactamente con lo reportado.

Se manda una vez por conexión, justo después de conectar y antes de la consulta real del usuario (`_sqlServerIsolateEntryPoint`), envuelta en su propio try/catch de mejor esfuerzo — si por lo que sea ese envío fallara, no bloquea la consulta real del usuario.

## 2026-07-24 — Bug real, confirmado con captura: el buscador jalaba el cursor mientras escribías en otro lado

## 2026-07-24 (continuación) — Optimización real del resaltado de sintaxis, medida antes de tocar código

Después de revertir la migración a `re_editor`, el usuario preguntó si valía la pena construir algo propio optimizado (inspirado en que `re_editor` corre su tokenización en un isolate aparte). En vez de asumir, se midió primero: un benchmark desechable (`test/_perf_bench_highlight.dart`, borrado después) contra scripts sintéticos mostró que `highlightSql` (el resaltador hecho a mano) tarda **~63ms por llamada en un script de 1000 líneas** — el tamaño real del cliente del usuario — casi 4x sobre los ~16ms que hacen falta para que se sienta fluido a 60fps. Como `buildTextSpan` corre en cada tecla, esto es un jank real, no teórico.

**Se descartaron los isolates** — mover la tokenización a un isolate aparte no es trivial aquí porque `TextEditingController.buildTextSpan` es síncrono por contrato (Flutter necesita el resultado YA para pintar ese frame); además el paso de ~200KB+ de texto entre isolates tiene su propio costo de serialización. Se optó por dos arreglos sin esa complejidad, ambos verificados con números reales antes de implementarlos:

**1. Algoritmo más rápido (`sql_syntax_highlighter.dart`), ~2.4x, mismo comportamiento exacto.** El resaltador viejo usaba un regex gigante con 50+ palabras clave alternadas (`\b(SELECT|FROM|...)\b`, insensible a mayúsculas) escaneado con `allMatches` sobre todo el segmento de código. Reescrito para tokenizar por palabra UNA vez (`_wordPattern`, un solo patrón sin alternación) y buscar cada palabra en un `Set<String>` (O(1)) en vez de re-probar ~50 alternativas por posición. Las palabras clave de dos palabras (`GROUP BY`, `LEFT JOIN`, etc.) se detectan con un lookahead de una palabra, **solo si el hueco entre ambas es puramente espacio en blanco** (para no confundir un `GROUP(BY` sin sentido con la palabra clave real — verificado con un test específico). Benchmark con el algoritmo nuevo: 26ms a 1000 líneas (todavía no alcanza los 16ms por sí solo, pero es la mitad del problema resuelta). 9 tests en `sql_syntax_highlighter_test.dart` (6 ya existentes, todos siguen pasando sin cambios — confirma que el comportamiento es idéntico — más 3 nuevos para el caso de dos palabras).

**2. El recálculo se debounce, no se dispara en cada tecla (`editor/highlighting_controller.dart`).** Mientras el texto sigue cambiando dentro de una ventana de 120ms desde la última tecla, `buildTextSpan` devuelve el texto actual (siempre correcto) sin colorear — barato, ~O(1) — y solo corre el resaltado real una vez que el usuario hace una pausa. **Restricción real que hubo que respetar con cuidado:** `buildTextSpan` debe devolver SIEMPRE el texto exacto actual — no se puede reusar un span "viejo" calculado con un texto distinto, porque el tamaño no cuadraría con el cursor real y lo desincronizaría. Por eso el fallback durante el debounce es texto plano sin color, nunca un resultado obsoleto.

**Bug real, encontrado por el test antes de llegar a producción:** la primera versión cancelaba y reiniciaba el timer de debounce cada vez que `buildTextSpan` se llamaba de nuevo mientras el recálculo seguía pendiente — pero eso puede pasar por razones que no son una tecla nueva (parpadeo del cursor, cualquier otro rebuild), lo que en teoría podía posponer el coloreado indefinidamente. Arreglado distinguiendo "el texto cambió desde la llamada anterior a `buildTextSpan`" (si acaba de pasar, sí reinicia el timer) de "el texto cambió desde el último recálculo real pero sigue igual desde la llamada anterior" (no toca el timer que ya viene contando). Se agregó `test/highlighting_controller_test.dart` (2 casos) que **capturó este bug en vivo**: revertí el arreglo a propósito, confirmé que el test fallaba exactamente como se esperaba, y luego apliqué el arreglo real.

También se le agregó `==`/`hashCode` a `SqlHighlightColors` — sin eso, la caché nunca hubiera funcionado, porque `sql_editor.dart` construye una instancia nueva en cada `build()` aunque los colores no cambien.

**Verificado:** `flutter analyze` limpio (bajó de 7 a 6 lints `info` preexistentes — el rewrite del highlighter de paso eliminó uno de los `if` sin llaves que arrastraba), `flutter test` **100/100** (95 previos + 5 nuevos).

## 2026-07-24 (continuación) — Investigación: mensajes/RAISE NOTICE (pausada), y bug real arreglado: el buscador no desplazaba la vista

**Investigación, sin implementar todavía (pausada a pedido del usuario):** preguntó por qué no ve la salida de `RAISE NOTICE` (PostgreSQL) en los resultados. Confirmado por código fuente, no supuesto: el paquete `postgres` (v3.5.12) sí recibe esos mensajes del servidor pero los descarta a propósito (`else if (message is NoticeMessage) { // ignore for now }`, `v3/connection.dart:517`) — no hay ninguna API pública para leerlos hoy. Arreglarlo de verdad implicaría: (1) forkear `postgres` (paquete nuevo, no hay fork todavía) para exponer los `NoticeMessage`, (2) modificar el fork de `mssql_connection` para acumular todos los mensajes en vez de solo el último y exponerlos, (3) llevar el concepto por conector → `QueryExecutionService` → resultado → una sección nueva de UI (tipo pestaña "Messages" de SSMS). La selección real se sigue moviendo también (para su resaltado visual nativo), pero ya no es de lo que depende el scroll. Misma limitación conocida que el popup de autocompletado: una línea envuelta (el editor no tiene scroll horizontal) puede desfasar el cálculo de línea para todo lo que venga después — aceptada, no se intentó resolver aparte.

**Tests:** `test/editor_search_controller_test.dart` actualizado — nuevo parámetro `onJumpTo` en el constructor, y assertions nuevas confirmando que saltar a una coincidencia SÍ dispara el callback con el offset correcto, y que editar el script en otro lado (sin buscar activamente) NO lo dispara.

## 2026-08-01 — Optimización de RAM en consultas masivas (~100k filas)

El usuario reportó que el consumo de RAM se dispara al ejecutar consultas que devuelven ~100k filas. Investigación (agente Explore, solo lectura) encontró dos causas concretas; se planificó con Plan Mode (plan en `C:\Users\Felix\.claude\plans\rustling-finding-cascade.md`) y se implementaron ambas en la misma sesión.

**Causa 1 — roundtrip JSON innecesario en SQL Server.** El pipeline pasaba por hasta 4 representaciones completas del resultset: Map nativo → `jsonEncode` a String completo → `jsonDecode` de vuelta a Map → copia al cruzar el `SendPort` del isolate. Se refactorizó `third_party/mssql_connection/lib/src/mssql_client.dart`: `_collectResults` se dividió en `_collectResultsRaw` (devuelve el Map directo, sin JSON) + un wrapper `_collectResults` que sigue devolviendo JSON para los demás llamadores (SET options, `executeParams`/inserción — sin tocar, payloads chicos). `execute()` se dividió igual en `_executeRaw`/`executeRaw()` público. `mssql_connection.dart` ganó `getDataRaw`. `sqlserver_connector.dart`'s `_sqlServerIsolateEntryPoint` ahora llama `getDataRaw` en vez de `getData`+`jsonDecode` — elimina el roundtrip JSON completo para el camino de SELECT.

**Causa 2 — `List<Map<String,Object?>>` como forma de cada fila.** Cada fila era un hashmap independiente (~40-48 bytes de overhead por entrada) en vez de una lista posicional + una lista de columnas compartida. Cambiado `RawQueryResult.rows`/`QueryResult.rows` a `List<List<Object?>>` en todo el pipeline:
- Postgres: `.toColumnMap()` (copia redundante — `ResultRow` del paquete ya es posicional) reemplazado por `List<List<Object?>>.from(result)`.
- SQL Server: el mismo refactor de la Causa 1 decodifica cada fila directo en `List<Object?>` posicional en vez de Map.
- Merge multi-bodega (`query_execution_service.dart`): de spread de Map a concatenación de listas.
- Grid (`virtualized_table.dart`) y export CSV (`results_pane.dart`): de `row[nombreColumna]` a `row[índice]` — en la mayoría de los casos el índice ya estaba disponible (`vicinity.column`), así que quedó más simple que antes, no más complicado.
- Sitios de introspección de esquema (autocompletado de tablas/columnas, árbol de esquema, definición de objetos — 5 archivos) también usan `RawQueryResult`, así que se adaptaron: los de una sola columna usan `row[0]` directo; los de varias columnas (`table_columns_provider.dart`, `schema_explorer_provider.dart`) usan un getter nuevo `RawQueryResult.rowMaps` que reconstruye el Map bajo demanda — solo para estos resultsets chicos (decenas de filas), nunca para el camino grande de resultados de usuario.

**Fuera de alcance, deliberado:** `DbConnector.insertRows` (importación CSV) sigue usando `List<Map<String,Object?>>` — es la forma natural de pasar parámetros nombrados a un INSERT parametrizado, y no es la ruta que reportó el problema.

**Verificado:** `flutter analyze` limpio (mismos lints info preexistentes, sin errores nuevos), `flutter test` 122/122 (tests actualizados: `query_execution_service_test.dart`, `database_discovery_service_test.dart` — literales de fila cambiaron de `{'col': val}` a `[val]`). **No confirmado en vivo todavía** — falta que el usuario corra la app contra el entorno Docker de prueba (bodegas con 5000 tablas) con una consulta real de ~100k filas y compare el consumo de memoria antes/después.

## 2026-08-02 — Paginación real (LIMIT/OFFSET) para consultas grandes

Cierre de la ronda de optimización de RAM: se implementó paginación real para que una consulta que devuelve ~100k filas ya no traiga todo a memoria antes de mostrar nada. Planificado con Plan Mode; antes de escribir el plan se investigó el driver `postgres` (v3.5.12): no tiene cursor de servidor nativo (`Statement.bind()` da un `Stream<ResultRow>` pero el protocolo extendido igual pide "todas las filas" al servidor, sin backpressure real) — un cursor real exigiría `DECLARE CURSOR`/`FETCH` manual dentro de una transacción persistente, lo cual bloquearía el resto de consultas de SQL Server (ya serializado a propósito). El usuario resolvió 3 decisiones de alcance vía `AskUserQuestion`:

1. **Mecanismo: `LIMIT`/`OFFSET` parametrizado** (no cursor) — más simple, con el costo aceptado de que páginas profundas re-escanean desde el inicio.
2. **Solo una base de datos por ahora** — "Consulta masiva" (multi-base) sigue trayendo todo de una, sin paginar.
3. **"Exportar CSV" siempre exporta el resultado completo**, no solo lo cargado — para una consulta paginada esto implica re-ejecutar la sentencia original (sin el LIMIT) antes de escribir el CSV.

**Implementación:**
- Nuevo módulo puro `lib/features/consulta/application/sql_pagination.dart` (+ `test/sql_pagination_test.dart`, 10 tests): `isPaginableSelect(statement)` (reutiliza `tokenizeSql` para ignorar strings/comentarios, confirma `SELECT`/`WITH` inicial y que no haya ya `LIMIT`/`OFFSET`/`TOP` propio) y `wrapForPage(statement, engine, {offset, fetchCount})` — envuelve como subquery `SELECT * FROM (...) AS _faro_page ...`; Postgres usa `LIMIT/OFFSET`, SQL Server usa `ORDER BY (SELECT NULL) OFFSET ... FETCH NEXT ... ROWS ONLY` (T-SQL exige `ORDER BY` para paginar). `paginationPageSize = 5000`, siempre se pide `pageSize + 1` para saber si hay más sin `COUNT(*)` aparte.
- `QueryRunState` ganó `paginated`/`hasMore`/`loadingMore`/`pagingTarget`/`pagingOriginalStatement` + un `copyWith`. `QueryRunActions` ganó `loadMore()`. Toda la lógica compartida vive en `consulta_providers.dart` como funciones libres reutilizadas por `QueryRunNotifier` y `TabQueryRunNotifier` (mismo patrón que `runStatementAndRecord`/`releasedRunState`): `preparePagination` (decide si envolver la última sentencia), `applyPaginationCap` (recorta la primera página + arma `hasMore`), `loadNextPage` (trae la siguiente página y la concatena, o si falla detiene la paginación mostrando el error en el mismo pill que ya se usa para fallos de consulta).

## 2026-08-02 (continuación) — Analizador léxico-sintáctico de SQL, `lib/sql_analysis/` (planificado con Plan Mode)

El diseño de la arquitectura (tipos de token, forma del AST, algoritmo del parser con recuperación de errores, alcance de la gramática v1) se validó con un agente de arquitectura dedicado antes de escribir el plan final — parser construction es un problema especializado.

**Implementado en 4 incrementos, cada uno verificado (`flutter analyze` + `flutter test`) antes de seguir al siguiente — sesión larga, control de calidad real en cada paso, varios bugs reales encontrados por los propios tests antes de darlos por buenos:**

1. **Lexer** (`lib/sql_analysis/lexer/`) — `lexSql(String) -> List<SqlToken>`, nunca lanza excepción (strings/comentarios/dollar-quotes sin cerrar corren hasta EOF en vez de fallar). Bug encontrado: faltaba `:` en el set de operadores, así que `::` (cast de Postgres) se partía en dos tokens sueltos.

2. **AST + parser** (`lib/sql_analysis/ast/`, `lib/sql_analysis/parser/`) — recursive descent a mano (sin dependencia nueva, mismo idioma que `sql_statement_resolver.dart`), con recuperación de errores real: `expect(...)` nunca consume el token equivocado cuando falta algo (ej. `FROM` sin tabla nunca se come `WHERE` como si fuera el nombre faltante). Alcance de la gramática: SELECT completo (FROM/JOIN/alias/subqueries/CTEs/UNION), INSERT/UPDATE/DELETE (columnas y alias con posición real) — todo lo que es "una expresión" (WHERE/HAVING/ON/SET) queda como rango opaco de tokens, sin árbol de precedencia (la decisión de alcance que hace tratable un parser escrito a mano). DDL completo (CREATE/ALTER/DROP/etc.) se reconoce pero no se parsea estructuralmente (`UnknownStatement`). Dos bugs reales encontrados por los tests: (a) mi primera versión de `_isNameToken` aceptaba *cualquier* keyword como nombre, así que `SELECT a FROM WHERE x = 1` se comía `WHERE` como la tabla faltante — corregido con una lista explícita de keywords "estructurales" que nunca cuentan como nombre; (b) el alias implícito sin `AS` (`SELECT a x FROM t`) no se detectaba porque el escaneo de la expresión no sabía de antemano dónde debía detenerse — corregido con lookahead explícito.

3. **Resolución de scope** (`lib/sql_analysis/analysis/scope_resolver.dart`) — `resolveScopeAt(statement, cursorOffset)` resuelve `p.` → `pedidos` respetando visibilidad léxica de CTEs (una CTE solo ve las declaradas antes que ella, más a sí misma si es RECURSIVE) y sin correlación en subqueries (simplificación deliberada — el scope exterior no se filtra hacia adentro de un subquery en FROM). Bug real encontrado: estaba agregando cada CTE dos veces (una como tabla del FROM sin resolver, otra como entrada de CTE aparte) — corregido para que el nombre en FROM se resuelva contra las CTEs en scope en vez de duplicarse.

4. **`sql_script_analyzer.dart`** — punto de entrada único del módulo (`analyzeSqlScript`), reusa `sql_statement_resolver.dart`'s `splitSqlStatements` en vez de reimplementar la división en sentencias. Diagnósticos ya vienen en coordenadas absolutas del script completo; los nodos del AST se quedan en coordenadas relativas a su propia sentencia (evita clonar recursivamente todo el árbol solo para sumar un offset) — `AnalyzedStatement.toAbsoluteOffset`/`toRelativeOffset` son la única conversión que hace falta.

**Integración con el editor real — alcance reducido deliberadamente, no conectado del todo.** El plan original preveía reemplazar `sql_autocomplete.dart`'s `_referencedTablePattern` (que confunde un `FROM` dentro de un string/comentario con uno real) y agregar subrayado de errores en `HighlightingController`. Se implementó y probó una versión corregida (`referencedTablesKeySafe`, usa el lexer para ignorar strings/comentarios) pero **no se conectó a los call sites reales de `sql_editor.dart`** — esos corren en cada keystroke sin debounce, y `sql_syntax_highlighter.dart` (2026-07-24) ya tuvo una regresión de rendimiento real y medida por exactamente ese patrón (análisis de texto sin debounce en un script de 1000 líneas), que necesitó su propio benchmark para arreglarse. El lexer nuevo hace estrictamente más trabajo por carácter que el tokenizer de 4 tipos que causó ese problema, así que conectarlo sin medir sería repetir el mismo error, no evitarlo. Queda listo y probado (con un test de rendimiento sintético informativo) para conectarse en una próxima ronda, una vez que se pueda medir contra la app corriendo de verdad.

**Verificado en cada incremento:** `flutter analyze` limpio en todo el proyecto, `flutter test` 257/257 al cierre (108 tests nuevos del módulo `sql_analysis` + `sql_autocomplete_test.dart` ampliado). **Nada de esto está conectado a la UI real todavía** salvo `referencedTablesKeySafe` (probada, pero sin wiring) — es un módulo nuevo, aislado, sin ningún cambio de comportamiento visible en la app tal como quedó hoy.

## 2026-08-02/03 (continuación) — Bug de memoria en mssql_client.dart arreglado; de paso, resuelto el bug de charset que estaba documentado como NO resuelto

Siguiente punto del checklist (`AUDITORIA_CODIGO.md`): la corrupción de memoria reportada en `third_party/mssql_connection/lib/src/mssql_client.dart:596` (`rpcVal.buf.length << 1` debía ser `>> 1` para el datalen de parámetros NVARCHAR en `dbrpcparam`). El usuario aclaró primero que los contenedores Podman activos (`sqlserver_maestromuebles`, `postgresql_*_texcoco/veracruz/tiendasmueblesrx_wms`) son datos reales de clientes y no deben tocarse — se levantó un contenedor SQL Server 2022 desechable aparte (`faro_verify_sqlserver`, imagen `mcr.microsoft.com/mssql/server:2022-latest` ya en caché local, puerto 14330, destruido al final de la sesión) para poder verificar el fix en vivo sin arriesgar nada real. Se escribió un script Dart standalone (`bin/verify_nvarchar_fix.dart`, temporal, ya borrado) que usa el paquete `mssql_connection` directo (no la app completa) para insertar/leer texto acentuado.

**El simple cambio `<<` → `>>` no era el fix real.** Al probarlo en vivo, `>> 1` (conteo de caracteres) hizo que SQL Server rechazara el INSERT con un error de protocolo ("invalid data length or metadata length"); probando con el byte length crudo (sin desplazamiento), el INSERT "funcionaba" pero el valor guardado salía corrupto (confirmado no por la propia lectura del driver, sino consultando `DATALENGTH()`/`LEN()`/`CAST(... AS VARBINARY)` directo en SQL Server y decodificando a mano). La causa real, confirmada empíricamente: `dbrpcparam` hace su PROPIO ensanchado interno de un byte a UCS-2 para parámetros `SYBNVARCHAR` — `datalen` es el conteo de bytes de SALIDA (post-ensanchado), no el conteo de caracteres ni el largo crudo de un buffer ya codificado en UTF-16LE (que es justo lo que el código, y su comentario, asumían — y que nunca se había puesto a prueba con contenido no-ASCII real, ni siquiera para los otros 2 usos ya existentes del mismo patrón en `@stmt`/`@params`).

**Fix real en `_encodeStringSmart`** (`mssql_client.dart`): strings no-ASCII ahora se codifican como Latin-1/ISO-8859-1 (1 byte por carácter) en vez de UTF-16LE, y el datalen pasa a ser `bufLen << 1` (el shift original, pero aplicado al buffer correcto) — se corrigió también en los otros 2 sitios (`@stmt`/`@params`, que usaban `>> 1`). Caracteres fuera del rango Latin-1 (código > 0xFF, ej. emoji) ahora lanzan `SQLException` explícita en vez de corromperse en silencio — verificado con un emoji de prueba.

**Bug relacionado, encontrado y arreglado de paso: resultó ser la causa real del bug de charset ya documentado como NO resuelto** (`project_faro_sqlserver_charset_fix.md`, tildes/ñ saliendo mal en resultados, ej. "Lácteos"). Al verificar el fix de escritura de arriba, la lectura de vuelta seguía corrupta — se agregó un print de diagnóstico temporal que reveló el `dbcoltype` real reportado para la columna NVARCHAR: **47 (`SYBCHAR`, no 103/`SYBNVARCHAR`)**, con `len` igual a la mitad de los bytes reales. Es decir: para esta conexión (según el charset del cliente negociado por FreeTDS), DB-Library entrega columnas NVARCHAR como si fueran de un solo byte por carácter (mapeo directo byte→código Unicode = Latin-1), no UTF-16LE ni UTF-8. El case `SYBCHAR`/`SYBVARCHAR`/`SYBTEXT` de `decodeDbValue` (`freetds_bindings.dart`) solo intentaba UTF-8 sin ningún respaldo — cualquier byte no-ASCII se convertía en U+FFFD en silencio. Corregido: si el decode UTF-8 sale con caracteres de reemplazo, se reintenta como Latin-1 (mismo patrón de respaldo que el case `SYBNVARCHAR` ya usaba entre UTF-16LE y UTF-8, pero aplicado al par correcto UTF-8/Latin-1).

**Verificado en vivo, round-trip completo:** escribir el texto original ("José Ñoño Muñoz - áéíóúÁÉÍÓÚñÑ - 'comilla' y 100% señal") y volver a leerlo da exactamente el mismo string — confirmado con `String ==`, no solo visualmente (la consola de Windows/bash no rendariza bien esos caracteres, así que la comparación real se hizo por código, no por inspección visual). Un lote de 20 inserts adicionales + un `LIKE '%señal%'` también funcionó correctamente (conteo exacto 21), descartando degradación por llamadas repetidas.

**Limpieza tras la verificación:** contenedor `faro_verify_sqlserver` destruido (`podman rm -f`), DLLs nativas copiadas temporalmente a `third_party/mssql_connection/` borradas, script `bin/verify_nvarchar_fix.dart` borrado, artefactos de `dart pub get` (`.dart_tool/`, `pubspec.lock`) borrados, ~20 procesos `dart.exe`/`dartvm.exe` huérfanos (acumulados por corridas repetidas del script de prueba) terminados. `third_party/mssql_connection/` quedó exactamente como estaba antes de esta investigación salvo los 2 archivos con el fix real.

Anotado en memoria para no asumir que solo falta `up -d`.

## 2026-08-03 (continuación) — Handler global de DB-Library corregido con mutex nombrado de Windows (multi-ventana)

Siguiente punto del checklist: el handler global de mensajes/errores de DB-Library (`dbmsghandle`/`dberrhandle`) puede colisionar entre isolates concurrentes, porque el callback Dart registrado (`Pointer.fromFunction`) solo es seguro de invocar desde el isolate que lo creó, pero DB-Library lo trata como global a todo el proceso.

**Confirmado que el riesgo es real, no solo teórico, antes de decidir el fix.** `SqlServerConnector._serialized` es una cola async, pero *por instancia* — y `core_providers.dart`'s `dbConnectorsProvider` es un `Provider` normal (no singleton global), así que cada `ProviderScope` (cada ventana, dado que cada ventana de Faro —principal y cada ventana de consulta vía `desktop_multi_window`— tiene su propio `ProviderScope`, confirmado en la memoria de multi-ventana) tiene su propia instancia de `SqlServerConnector` con su propia cola independiente. Todas las ventanas comparten el mismo proceso del sistema operativo (confirmado también en esa memoria), así que dos ventanas SÍ pueden llamar a DB-Library genuinamente en paralelo — exactamente el escenario que dispara la colisión.

**Opciones evaluadas con el usuario vía pregunta directa:** mutex nombrado de Windows (nuevo FFI acotado) vs. lock-server en Dart puro vía `IsolateNameServer` (más superficie de bugs de ciclo de vida) vs. posponer vs. investigar primero qué tan reproducible es. **El usuario eligió el mutex nombrado de Windows.**

**Implementación** (`lib/data/datasources/sqlserver_connector.dart`, nueva clase `_SqlServerProcessLock`): bindings FFI propios para `CreateMutexW`/`ReleaseMutex` (mismo patrón ya usado en `native_loader.dart` para `SetDllDirectoryW`/etc. — `DynamicLibrary.open('kernel32.dll')` + `lookupFunction`), reutilizando `WaitForSingleObject`/`CloseHandle` que `package:win32` ya expone. El mutex (`Local\FaroSqlServerDbLibLock`) envuelve la sesión COMPLETA de DB-Library (conectar→SET ANSI→consulta/insert→desconectar), no solo el `connect()`, porque un mensaje/error puede llegar en cualquier momento de la consulta, no solo al conectar. Aplicado en los 3 puntos de entrada: `testConnection` (corre en el isolate propio del conector) y los dos entry-points de isolate desechable (`_sqlServerIsolateEntryPoint` para `runQuery`, `_sqlServerInsertIsolateEntryPoint` para `insertRows`).

**Decisiones de diseño clave:**
- Espera acotada (`WaitForSingleObject` con timeout de 30s, no infinita) en vez de esperar para siempre — si alguna vez el lock queda tomado sin liberarse, el usuario ve un error claro ("no se pudo obtener acceso exclusivo... otra ventana está usando SQL Server") en vez de que toda consulta futura, en cualquier ventana, se cuelgue para siempre. `WAIT_ABANDONED` (el hilo dueño anterior murió sin liberar) se trata como adquisición exitosa, semántica estándar de Windows.
- El handle se cierra (`CloseHandle`) después de cada uso, no se cachea — cada isolate desechable de Faro solo llama esto una vez en su vida útil (una consulta = un isolate = una llamada), así que cachear no ahorra nada; y un HANDLE de Windows pertenece al *proceso*, no al hilo/isolate que lo creó, así que no cerrarlo hubiera goteado un handle real por cada consulta ejecutada, para siempre, mientras la app siga abierta.
- Se razonó sobre qué pasa si se cancela una consulta (`Isolate.kill`) mientras el isolate tiene el mutex tomado: la propia documentación existente de `SqlServerConnector` ya explica que una llamada nativa bloqueante sigue corriendo en segundo plano tras el kill hasta que se desbloquea sola — es decir, el `finally` que libera el mutex sigue ejecutándose cuando la llamada nativa por fin retorna, antes de que el isolate realmente se destruya. El timeout de 30s queda como respaldo para cualquier caso no anticipado.

**Verificado en vivo, no solo con tests unitarios (imposible sin una condición de carrera real):** contenedor SQL Server desechable nuevo (mismo patrón que sesiones anteriores, destruido al terminar) + script temporal (`test/_tmp_lock_verify.dart`, borrado después) que lanza 2 isolates, cada uno creando su propia instancia real de `SqlServerConnector` (simulando 2 ventanas) y ejecutando `WAITFOR DELAY '00:00:02'; SELECT ...` casi al mismo tiempo. ## 2026-08-04 (continuación) — Prioridad 2: primer ítem del driver nativo (contrato de cancelación en `insertRows`), con una investigación en vivo más larga de lo esperado

Usuario pidió empezar por los 8 ítems de Prioridad 2 recién encontrados (todos en la capa de datos/driver nativo). Se resolvió el primero — **contrato de cancelación inconsistente en `insertRows`: Postgres devuelve un `BulkInsertOutcome` parcial al cancelar, SQL Server mataba el isolate entero y perdía el conteo** — y se decidió pausar ahí por hoy dado lo profunda que resultó la investigación.

**Contexto real primero:** confirmado por grep que `insertRows` solo se llama desde un lugar en toda la app (`csv_import_service.dart:221`) y **ese call site nunca pasa un `CancellationToken`** — la inconsistencia era 100% inalcanzable en producción hoy, pero el contrato de la interfaz (documentado en `DbConnector.insertRows`) sí promete soporte de cancelación, y es una brecha real para cualquier futuro botón "cancelar importación".

**Diseño del fix:** el isolate de inserción de SQL Server (`_sqlServerInsertIsolateEntryPoint`) ahora crea su propio `ReceivePort` para cancelación, envía su `SendPort` de vuelta al padre como primer mensaje (`{'type': 'cancelPort', ...}`), y el padre (`_insertRowsInIsolate`) reenvía la señal de `cancellationToken.onCancel` a través de ese puerto en vez de matar el isolate de inmediato. El loop de filas chequea `cancelled` entre cada una (misma granularidad que ya usa `PostgresConnector.insertRows`) y, al cancelar, envía un `BulkInsertOutcome` parcial real por el mismo canal de mensajes normal, en vez de que el padre nunca reciba nada. Un `Future.delayed` de 5 segundos como red de seguridad sigue matando el isolate igual que antes si la ruta graceful nunca responde (isolate genuinamente atascado en una llamada nativa).

**La parte que tomó más tiempo — descubrir por qué la cancelación no llegaba a tiempo:** en las primeras pruebas en vivo (contenedor SQL Server 2022 desechable vía Podman), la cancelación fallaba consistentemente y caía al timeout de 5 segundos. Diagnóstico paso a paso:
1. Confirmado con mensajes de depuración (enviados por el mismo canal de `SendPort`, no `print` — un `print` dentro de un isolate que luego se mata con `Isolate.kill(priority: immediate)` se pierde, ya que el kill no espera a que se vacíen los buffers de salida) que el mensaje de cancelación **sí llegaba**, pero tarde — después de que el loop ya había podido, en teoría, revisarlo muchas veces.
2. Causa raíz: `connection.writeDataWithParams(...)` es una llamada FFI bloqueante por debajo de su `Future` — su `await` se resuelve sin nunca devolver el control a la cola de eventos del isolate. Dart vacía la cola de microtasks por completo antes de revisar la cola de eventos (donde vive el mensaje entrante del `ReceivePort`) — un loop de `await`s que se resuelven así, fila tras fila, puede inanir la cola de eventos indefinidamente.
3. Un `Future.delayed(Duration.zero)` entre filas (intento de forzar un tick real) **resultó no confiable** — a veces funcionaba, a veces no, sin patrón claro al principio.
4. Cambiar a un `Future.delayed` con duración real (1ms, no cero) sí forzó un tick de verdad de forma consistente — pero con un costo de rendimiento real (~4x más lento en un insert de 2000 filas).
5. Intentar reducir el costo revisando cada 20 filas en vez de cada una **rompió la confiabilidad de nuevo** — y aquí apareció el hallazgo más interesante: la falla no era sobre la frecuencia del yield en sí, sino sobre **cuántos isolates ya habían corrido antes en el mismo proceso**. Un script de prueba simple (pocos isolates previos) funcionó consistente (3/3) incluso con el yield cada fila; el mismo código en un script más elaborado (varios inserts grandes antes de la prueba de cancelación) falló repetidamente incluso con yield en cada fila. Esto sugiere una degradación de estado nativo acumulada a través de muchos ciclos connect/disconnect dentro del mismo proceso — posiblemente relacionada con el propio ítem pendiente "`LOGINREC` nunca se libera" (leak en cada `connect()`).

**Decisión final, con el límite documentado explícitamente en vez de perseguir una solución perfecta:** el yield (`Future.delayed` de 1ms) solo se paga cuando el caller realmente pasa un `CancellationToken` (nuevo campo `hasCancellationToken` en el request del isolate) — como el único call site real hoy no lo hace, el camino de producción actual queda exactamente a la misma velocidad que antes de este fix, verificado en vivo (2000 filas: ~6.2s con o sin el cambio). Cuando SÍ se pasa un token, funciona de forma confiable en un proceso "fresco" (verificado 3/3 corridas limpias) pero puede degradarse a la conducta anterior (kill abrupto, se pierde el parcial) después de mucho desgaste de isolates en el mismo proceso — nunca peor que el comportamiento previo a este fix, simplemente no siempre mejor. Documentado así en `AUDITORIA_CODIGO.md`, sin pretender que quedó perfectamente resuelto.

**Verificado:** `flutter analyze` limpio (6 lints info preexistentes), `flutter test` 309/309 (sin tests nuevos — la lógica vive enteramente en isolates/FFI sin cobertura de test Dart posible, verificado en vivo en su lugar contra un contenedor SQL Server 2022 desechable, destruido al terminar). Scripts de verificación temporales (`tool/verify_cancel.dart`, `tool/verify_cancel2.dart`) creados y borrados al terminar — no quedan en el repo.

**Pausa decidida por el usuario:** dado lo profunda que resultó esta sola investigación, se preguntó cómo continuar con los 7 ítems restantes de Prioridad 2 (mismo nivel de profundidad vs. más rápido vs. pausar) — el usuario eligió **pausar aquí por hoy**. Quedan pendientes los mismos 7 ítems de la entrada anterior (todos en el driver nativo), más los 3 de Prioridad 3 y el `AutocompleteController` de `sql_editor.dart`.

## 2026-08-04/05 (continuación) — 6 de los 7 ítems restantes de Prioridad 2, y uno investigado pero deliberadamente no arreglado

Usuario retomó con "si vamos". Se resolvieron 6 de los 7 ítems restantes de Prioridad 2 (todos en el driver nativo vendorizado), cada uno verificado en vivo contra un contenedor SQL Server 2022 desechable (Podman, destruido al terminar cada uno) salvo donde se anota lo contrario. El último ítem se investigó a fondo pero se decidió no tocarlo — ver el cierre de esta entrada.

1. **`LOGINREC` nunca se libera** (leak en cada `connect()`): agregado el binding faltante a `freetds_bindings.dart` y llamado justo después de `dbopen()` (cubre éxito y fallo por igual) y en el punto de fallo de credenciales (antes de llegar a `dbopen`). **Hallazgo real durante la implementación:** el nombre de símbolo que asumía el ítem original (`dbfreelogin`) no existe en el `sybdb.dll` vendorizado — confirmado con `grep` directo sobre los bytes del `.dll` antes de escribir el binding (mismo método ya usado, `grep -a` sobre el binario). El nombre real es `dbloginfree`. Verificado en vivo: 20 ciclos connect/query/disconnect seguidos sin crash, una conexión con password incorrecto (ejercita el punto de liberación antes de `dbopen`) sin crash, y una reconexión exitosa inmediatamente después con datos correctos.
2. **Tipos `date`/`time`/`datetime2`/`datetimeoffset` sin caso en el switch de decodificación**: el diagnóstico del ítem original resultó incompleto una vez verificado en vivo — `dbconvert` casi nunca falla para estos tipos (el "degrada a base64" casi nunca se dispara), pero su string de salida por defecto es el formato legado de Sybase (`"Mar 15 2024  1:45:30:1234567PM"`), no ISO 8601, y para un valor `TIME`/`DATE` puro rellena la mitad que le falta con un placeholder sin sentido (`Jan 1 1900` para TIME, `12:00:00:AM` para DATE) — el tipo de cosa que corrompería en silencio cualquier código que espere una fecha ISO real después (CSV export, `DateTime.parse`, orden por string). Nueva `_sybaseDateTimeStringToIso` reparsea ese string a ISO 8601 real vía regex, descartando la mitad placeholder para DATE/TIME puros — decisión deliberada de reparsear el string de `dbconvert` en vez de decodificar a mano los bytes crudos del wire TDS (largo variable según el `scale` de la columna, más riesgoso de acertar con confianza). **Límite conocido, no oculto:** para `DATETIMEOFFSET`, `dbconvert` ya perdía el offset de zona horaria desde antes de este fix (no es una regresión) — el fix corrige el formato pero no recupera el offset; eso necesitaría decodificar a mano los 2 bytes finales del payload crudo, no intentado hoy. Verificado en vivo con las 6 combinaciones de tipo/precisión (`DATE`, `TIME`, `TIME(3)`, `DATETIME2`, `DATETIME2(7)`, `DATETIMEOFFSET`) — las 5 primeras ISO 8601 exacto, la sexta ISO 8601 sin offset (esperado).
3. **`DECIMAL`/`NUMERIC` convertido a `double`** (pérdida de precisión): cambiado de `dbconvert(..., SYBFLT8, ...)` a `dbconvert(..., SYBVARCHAR, ...)` — string exacto en vez de double con pérdida. Se confirmó primero que el paquete `postgres` (usado por `PostgresConnector`) YA devuelve `numeric` como `String` (`text_codec.dart`, `case TypeOid.numeric: return asText();`) — el fix iguala ambos motores en vez de dejar una inconsistencia nueva. Se revisó `virtualized_table.dart`'s `_typeFor` (clasifica columnas como "decimal" solo si `value is double`) para confirmar que el cambio no introduce una regresión NUEVA: Postgres NUMERIC ya se clasifica como "texto" hoy por la misma razón, así que SQL Server pasando a comportarse igual es consistencia, no una regresión adicional. Verificado en vivo: `DECIMAL(18,2)` (19.99, 0.10), `NUMERIC(18,4)` con 16 dígitos significativos (123456789012.3456, más allá de lo que un `double` puede representar con confianza) y un valor negativo (-42.50) — los 4 exactos, dígito por dígito.
4. **`_lastMessage` nunca se limpia en éxito**: nueva `DBLib.clearMessages(dbproc)` (limpia `_lastError`/`_lastMessage` para esa dirección), llamada en `connect()` justo tras `dbopen()` exitoso. Cierra ambas mitades del bug original a la vez: un mensaje de una sentencia exitosa (p. ej. un `PRINT`) que nadie consume ya no puede sobrevivir indefinidamente, y una dirección de `DBPROCESS` reciclada por el sistema operativo para una conexión nueva y completamente distinta ya no hereda mensajes de quien la usó antes. Verificado en vivo: un `PRINT` exitoso seguido de un error real (`SELECT` a tabla inexistente) reporta el mensaje del error real, no el `PRINT` anterior; reconexión posterior funciona con datos correctos.
5. **Fallos de BCP no limpian el estado BCP de la conexión**: nueva bandera `bcpFinished`, marcada `true` justo después del `bcp_done()` del camino feliz — un `finally` que envuelve todo desde `bcp_bind` hasta el `return` llama `bcp_done()` una segunda vez (best-effort, sin relanzar) solo si esa bandera sigue en `false`, cubriendo cualquier excepción de `bcp_bind`/`bcp_sendrow`/`bcp_batch`/el propio `bcp_done`. Sin verificación en vivo — `bulkInsert` (el camino BCP real) confirmado por grep que no se llama desde ningún lugar de la app hoy, mismo criterio ya aplicado a otros ítems de esta familia en sesiones anteriores.
6. **Fallback `#temp` de `bulkInsert` "no atómico"**: el diagnóstico del ítem original también resultó distinto una vez revisado el contexto completo — envolver esto en una transacción habría sido el fix *incorrecto*, ya que `DbConnector.insertRows` (la capa que llama a este fallback) documenta explícitamente que cada fila debe ejecutarse como una sentencia independiente auto-commiteada a propósito (una fila mala no debe bloquear al resto; en Postgres una sentencia fallida dentro de una transacción explícita envenena las siguientes). Este fallback ya seguía ese contrato; el bug real era que `executeParams(...)` no estaba dentro del `try/catch` (solo el `jsonDecode` posterior lo estaba), así que un fallo genuino a mitad de camino (conexión caída, no solo "esta fila tenía datos inválidos") descartaba el conteo `total` completo al propagarse fuera de `bulkInsert`. Ahora `executeParams` también está dentro del `try`, mismo criterio de "sin verificación en vivo, sin impacto en producción hoy" que el ítem anterior.

**El 7mo ítem, "sin primitiva de cancelación real en el paquete", se investigó a fondo y se decidió deliberadamente NO tocarlo hoy.** Confirmado el mecanismo exacto: `_sqlServerIsolateEntryPoint`'s `connection.disconnect()` vive en un `finally` que envuelve la llamada bloqueante (`getDataRaw`/`dbsqlexec`); `isolate.kill(priority: Isolate.immediate)` (usado al cancelar) termina el isolate sin honrar ese `finally` si el kill llega mientras la llamada nativa sigue bloqueada. Se consideraron y descartaron dos rutas de arreglo:
- **El padre cierra la conexión directamente**, usando la misma dirección de puntero que el hijo (el hijo la manda temprano por mensaje). Descartada: si el hijo sigue genuinamente bloqueado dentro de una llamada nativa sobre ese mismo `DBPROCESS` en el momento del cierre, el padre estaría tocando la misma estructura DB-Library concurrentemente desde otro isolate — exactamente la clase de carrera que `_SqlServerProcessLock` (arreglado esta sesión, días atrás) existe para prevenir. Un cierre concurrente ahí sería una condición de carrera a nivel nativo con riesgo real de crash, peor que el leak que se intenta resolver.
- **El mismo patrón de yield usado ayer para `insertRows`** (ceder el control periódicamente entre iteraciones para observar una señal de cancelación). No aplica: `runQuery` ejecuta una sola llamada bloqueante de principio a fin, sin loop de filas ni puntos de chequeo naturales entre medio.

Es una limitación arquitectónica real del driver FFI síncrono (ya reconocida en el propio comentario de clase de `SqlServerConnector`), no un descuido corregible con una función. Resolverla de verdad necesitaría cambios en el propio driver FreeTDS vendorizado o un rediseño mayor (pool de conexiones persistentes) — fuera de alcance razonable hoy. Queda sin marcar en el checklist, con la investigación completa anotada ahí mismo para no repetirla desde cero en el futuro.

El usuario reportó, usando la app contra datos reales de cliente (no se tocó ningún dato ni contenedor real — el diagnóstico se hizo con scripts standalone puros en Dart, sin conexión a base de datos): (1) un script con un comentario en la primera línea no corre, dice "no se reconoce como SELECT válido"; (2) quiere que el nombre del CSV exportado incluya palabras clave de la consulta y el nombre+IP de la base de datos, tanto en export individual como masivo; (3) quiere un campo de IP en los resultados de consulta masiva, no solo el nombre de base de datos.

**1. Bug bloqueante: comentario inicial rompe la ejecución (real, reproducido con un script de diagnóstico standalone antes de tocar nada).** `SqlGuard.assertReadOnly` en sí ya manejaba comentarios iniciales correctamente (tests existentes lo confirman) — el bug real estaba un nivel más abajo, en `splitSqlStatements`/`_splitByStatementKeywordLines` (`lib/sql_analysis/analysis/script_splitter.dart`), usado cuando el script no tiene ningún `;`. Reproducido exacto: `/* nota */\nSELECT * FROM productos` se partía en DOS "sentencias" — el comentario solo, y el SELECT — porque el salto de comentario `/* */` (a diferencia del de `--`, que sí salta el `\n` siguiente) se detenía justo después del `*/` sin consumir el salto de línea, dejando que el chequeo de "¿esta línea empieza con keyword?" viera ese `\n` directamente y creara una frontera de sentencia ahí mismo. El comentario-solo, sin nada de SQL real, fallaba el guard de solo-lectura ("no se reconoce como SELECT"), y como la ejecución para en la primera sentencia que falla, el SELECT real nunca corría. **El mismo problema ya existía para comentarios `--` también** (nadie lo había reportado con ese estilo) — confirmado con un caso de prueba antes de arreglar nada. Fix: en vez de simplemente igualar el comportamiento de `/* */` al de `--` (lo cual habría fusionado incorrectamente dos sentencias reales separadas solo por un comentario, verificado que rompía ese caso en una primera versión del fix), se agregó un flag `sawContentSinceBoundary` que rastrea si ya hubo contenido real (no comentario, no espacio) desde la última frontera — el salto de línea tras un comentario solo se consume cuando el comentario es lo *primero* en el bloque actual (el caso reportado), dejando intacto el comportamiento cuando el comentario separa dos sentencias reales genuinas. 12 tests nuevos (`test/sql_statement_resolver_test.dart`) cubriendo ambos estilos de comentario, comentarios de bloque multilínea, y el caso de "dos sentencias reales separadas por un comentario" para confirmar que no se fusionan.
